# Skill: Performance Profiling & Optimization

**Железный принцип:** СНАЧАЛА ИЗМЕРЬ, не угадывай. Оптимизируй ТОЛЬКО доказанный профилировщиком bottleneck — всё остальное это слепая трата времени и риск регрессии.

> Закон Кнута: *"Premature optimization is the root of all evil"* — но полностью звучит так: «мы должны забыть о малой эффективности в ~97% случаев; преждевременная оптимизация — корень всех зол. И всё же мы не должны упускать наши возможности в критических 3%.» Профайлинг — это инструмент, который находит эти 3%.

## Когда активировать

- Пользователь говорит «тормозит / медленно / лагает / зависает», просит «ускорить» или «оптимизировать».
- Регрессия: «вчера работало быстро, сегодня медленно», p95/p99 латентности вырос.
- Запрос/эндпоинт/страница не укладывается в SLA или budget (см. бюджеты ниже).
- Рост потребления памяти/CPU, OOM-килл, утечка под нагрузкой.
- Перед нагрузочным релизом — снять baseline и убедиться, что нет очевидных N+1 / отсутствующих индексов.

**НЕ активировать** для микро-tweak'ов кода, который выполняется редко и не на горячем пути (это анти-паттерн, см. ниже).

## Метод (7 шагов — нарушать порядок нельзя)

Это алгоритм. Каждый шаг даёт артефакт для следующего. Пропуск шага = угадывание.

```
1. BASELINE   Воспроизведи + замерь ТЕКУЩЕЕ. Зафиксируй число (p50/p95, RPS, RSS, мс).
              Нет числа ДО → нечем доказать улучшение. СТОП, измерь.
2. PROFILE    Запусти профилировщик под нагрузкой/типовым сценарием (см. таблицу стеков).
              Собери wall-clock И/ИЛИ CPU И/ИЛИ allocations — что релевантно симптому.
3. HOTSPOT    Найди горячую точку ПО ДАННЫМ профиля: где cumulative time / allocs / calls.
              Правило 80/20: один-два фрейма обычно дают >50% времени. Туда и смотри.
4. HYPOTHESIS Сформулируй ОДНУ гипотезу: "X медленный, потому что Y (N+1 / нет индекса /
              sync I/O в async / лишние аллокации / нет кэша)". Запиши до фикса.
5. FIX        Минимальное изменение, бьющее ровно в гипотезу. Один фактор за раз.
              Без "заодно отрефакторю" — это ломает атрибуцию дельты.
6. REMEASURE  Прогони ТОТ ЖЕ замер, что в шаге 1, тем же способом, теми же данными.
7. CONFIRM    Посчитай дельту: Δ% = (после − до)/до × 100. Speedup = до/после.
              Подтверди, что bottleneck сместился (перепрофилируй). Нет дельты → откати.
```

**Инвариант:** число ДО (шаг 1) и число ПОСЛЕ (шаг 6) сняты **идентично** — те же входные данные, тот же warm-up, тот же режим (prod-like, не debug). Иначе дельта недоказуема.

## Бюджеты и пороги (когда вообще стоит чинить)

| Контекст | Зелёный | Жёлтый (смотреть) | Красный (чинить) |
|---|---|---|---|
| HTTP API p95 latency | < 100 мс | 100–300 мс | > 300 мс |
| HTTP API p99 latency | < 300 мс | 300–1000 мс | > 1 с |
| SQL запрос (OLTP) | < 10 мс | 10–100 мс | > 100 мс |
| Web LCP (Core Web Vitals) | ≤ 2.5 с | 2.5–4.0 с | > 4.0 с |
| Web INP (отзывчивость) | ≤ 200 мс | 200–500 мс | > 500 мс |
| Web CLS (сдвиг макета) | ≤ 0.1 | 0.1–0.25 | > 0.25 |
| JS main-thread task | < 50 мс | 50–200 мс | > 200 мс |
| Перцептивный порог (Nielsen) | мгновенно < 100 мс · «течёт» < 1 с · удержание внимания < 10 с | | |

Long task (по Long Tasks API) — это любая задача main-thread **> 50 мс**; от ~200 мс она ощутимо вредит INP.

**Ключевые числа латентности (Latency Numbers, порядки):** L1 ≈ 1 нс · RAM ≈ 100 нс · SSD random read ≈ 16 мкс · сеть внутри ДЦ round-trip ≈ 0.5 мс · диск seek (HDD) ≈ 10 мс · TCP пакет CA↔Netherlands round-trip ≈ 150 мс. Запоминай порядки: один round-trip внутри ДЦ (0.5 мс) ≈ **5 000** обращений к RAM (100 нс); межконтинентальный (150 мс) ≈ 1.5 млн. N+1 запрос превращает 1 round-trip в N — вот почему он так бьёт.

## Инструменты по стеку

| Стек | Что мерить | Инструмент | Команда / приём |
|---|---|---|---|
| **Python (CPU/wall)** | где время | `cProfile` + `pstats` | `python -m cProfile -o out.prof app.py` → `pstats` сорт по `cumulative` |
| Python (sampling, прод) | без инструментации | `py-spy` | `py-spy top --pid PID` · `py-spy record -o fg.svg --pid PID` (flamegraph) |
| Python (память) | аллокации/утечки | `tracemalloc` | `tracemalloc.start()` → `snapshot.compare_to(prev,'lineno')` |
| Python (line-level) | строка за строкой | `line_profiler` | `@profile` + `kernprof -l -v script.py` |
| Python (memory leak) | рост объектов | `objgraph` / `gc` | `objgraph.show_growth()` между точками |
| **Node.js (CPU)** | где время | V8 `--prof` / `clinic` | `node --prof app.js` → `--prof-process` · `clinic flame -- node app.js` |
| Node.js (event loop) | блокировки loop | `clinic doctor` | `clinic doctor -- node app.js` (диагноз: I/O / GC / event loop) |
| Node.js (память) | heap/утечки | `--inspect` + DevTools | heap snapshot, сравнить два снимка |
| **SQL** | план запроса | `EXPLAIN ANALYZE` | PG: `EXPLAIN (ANALYZE, BUFFERS) <q>` — ищи `Seq Scan`, высокий `rows`, `Nested Loop` × N |
| SQL (медленные) | топ запросов | `pg_stat_statements` | сорт по `total_exec_time` / `mean_exec_time` |
| **Web frontend** | загрузка/отзывчивость | Lighthouse / DevTools Perf | `lighthouse URL --output json` · Performance panel → Long Tasks |
| Web (поле, реальные юзеры) | Core Web Vitals | `web-vitals` / CrUX | RUM: LCP, INP, CLS с перцентилями |
| **Bundle size** | вес JS | `source-map-explorer` / webpack-bundle-analyzer | визуализация что раздувает бандл |
| **Общая (HTTP load)** | RPS, latency dist | `wrk` / `ab` / `hey` | `wrk -t4 -c100 -d30s URL` · `ab -n 10000 -c 100 URL` |
| Общая (wall-clock) | время процесса | `time` / `hyperfine` | `/usr/bin/time -v cmd` (+ RSS) · `hyperfine 'cmd'` (статистика по N прогонам) |
| Общая (system) | CPU/IO/syscalls | `perf` / `strace` / `htop` | `perf record -g cmd` · `strace -c -f cmd` (счётчик syscalls) |

**Правило выбора:** dev/локально и можно остановить процесс → детерминированный профайлер (`cProfile`, `--prof`). Прод/живой процесс нельзя трогать → sampling (`py-spy`, `perf`) — он почти не добавляет overhead.

## Частые паттерны и их фиксы

| Паттерн (симптом в профиле) | Корень | Фикс | Типичный выигрыш |
|---|---|---|---|
| **N+1 query** (1 запрос + N в цикле; в профиле — драйвер БД доминирует по calls) | ленивая загрузка связей в цикле | eager load / JOIN / `IN (...)` / DataLoader-батчинг · ORM: `select_related`/`prefetch_related`, `.options(joinedload)` | N сетевых round-trip → 1–2; часто 10–100× |
| **Нет индекса** (`Seq Scan` на большой таблице, `rows` >> возвращаемых) | фильтр/join по неиндексированной колонке | `CREATE INDEX ON t(col)` · композитный индекс под `WHERE`+`ORDER BY` · покрывающий (`INCLUDE`) | O(n) скан → O(log n); 10–1000× на больших таблицах |
| **Sync I/O в async-коде** (event loop заблокирован; в `clinic doctor` — "event loop") | блокирующий вызов (`requests`, `open`, `time.sleep`, sync-драйвер) в корутине | async-аналог (`httpx`/`aiohttp`, `aiofiles`, `asyncio.sleep`) или `asyncio.to_thread()` / `run_in_executor` | разблокирует конкуренцию; throughput ×(число конкурентных операций) |
| **Лишние аллокации/копии** (в `tracemalloc` — много мелких объектов; GC давит) | копирование в цикле, `list`+`+=`, конкатенация строк | генераторы, `"".join()`, переиспользование буферов, `__slots__`, `array`/numpy для числовых | меньше GC-пауз, меньше RSS; 2–5× на горячих циклах |
| **Нет кэша/мемоизации** (один и тот же дорогой расчёт повторяется) | пересчёт детерминированного результата | `functools.lru_cache`/`cache`, Redis/memcached, HTTP-кэш, memoize по ключу | повторные вызовы → ~O(1); зависит от hit-rate |
| **Чрезмерная сериализация** (json/pickle доминирует в профиле) | сериализуем больше, чем нужно; медленный сериализатор | отдавать только нужные поля, `orjson`/`msgpack` вместо stdlib `json`, пагинация, сжатие | 2–10× на сериализации; меньше payload |
| **Неленивая загрузка** (грузим всё, используем часть) | `SELECT *`, чтение всего файла, eager-import тяжёлых модулей на старте | проекция колонок, стриминг/итерация, `LIMIT`, lazy-import, пагинация | меньше I/O и памяти пропорционально неиспользованному |
| **Algorithmic O(n²)** (время растёт квадратично с N) | вложенный цикл / `in` по списку | `set`/`dict` для lookup (O(1)), сортировка+two-pointer, правильная структура данных | O(n²) → O(n) или O(n log n) |

## Формат ответа

```
⚡ Performance: [что профилировали]

📏 ДО (baseline):  [метрика] = [число] ([как мерили: инструмент, нагрузка, данные])
🔥 Горячая точка:  [фрейм/запрос/строка] — [X% времени | Y аллокаций | N calls]
                   (из профиля: [конкретная цифра из cProfile/EXPLAIN/flamegraph])
💡 Гипотеза:       [паттерн] — [почему именно он]
🔧 Фикс:           [минимальное изменение, 1-2 строки сути]
📏 ПОСЛЕ:          [метрика] = [число] (тем же способом)
📊 Дельта:         −Z% времени  ·  speedup ×K  ·  bottleneck сместился на [новое]

[если красный порог остался] Следующий кандидат: [...]
[если упёрлись] Дальше выигрыш < 10% — не трогаю (см. границы).
```

## Worked example: N+1 в эндпоинте заказов

**Симптом:** `GET /orders` отдаёт 200 заказов за ~1.8 с, p95 в красной зоне (> 300 мс).

**Шаг 1 — baseline.** Замер тем же запросом, прогретый кэш ОС:
```bash
hyperfine --warmup 3 'curl -s localhost:8000/orders > /dev/null'
# Time (mean ± σ):  1.812 s ±  0.041 s   [User: 0.006s, System: 0.004s]
```

**Шаг 2 — profile.** Под нагрузкой смотрим, где время:
```bash
py-spy record -o orders.svg --pid $(pgrep -f uvicorn) -d 20
# либо детерминированно:
python -m cProfile -o orders.prof bench_orders.py
python -c "import pstats; pstats.Stats('orders.prof').sort_stats('cumulative').print_stats(8)"
```
Вывод pstats (сокращённо):
```
   ncalls  cumtime  percall  filename:lineno(function)
      201    1.640   0.008   psycopg2: execute        <- 201 вызовов БД!
        1    0.040   0.040   serializers.py:dump
```

**Шаг 3 — hotspot.** 201 вызов БД (1 список + 200 на `order.customer.name` в цикле) дают 1.64 с из 1.81 с = **91% времени**. Классический N+1.

**Шаг 4 — гипотеза.** Ленивая загрузка `order.customer` внутри цикла сериализации → 200 отдельных round-trip к БД.

**Шаг 5 — fix (минимальный).** Eager-load связи одним запросом:
```python
# было
orders = session.query(Order).all()
# стало
orders = session.query(Order).options(joinedload(Order.customer)).all()
```

**Шаг 6+7 — remeasure & confirm:**
```bash
hyperfine --warmup 3 'curl -s localhost:8000/orders > /dev/null'
# Time (mean ± σ):  0.094 s ±  0.003 s
```
```
⚡ Performance: GET /orders (200 заказов)
📏 ДО:        mean 1.812 s (hyperfine, warmup 3, прод-данные)
🔥 Горячая:   psycopg2.execute — 201 call, 1.64 s = 91% (cProfile cumulative)
💡 Гипотеза:  N+1 — order.customer ленится в цикле
🔧 Фикс:      joinedload(Order.customer) → 201 запрос стал 1
📏 ПОСЛЕ:     mean 0.094 s
📊 Дельта:    −94.8% · speedup ×19.3 · bottleneck сместился на serializers.dump (теперь 43%)

Следующий кандидат: сериализация (orjson дал бы ещё ~2×), но 94 мс уже в зелёной зоне p95 — стоп.
```

Проверка арифметики: Δ% = (0.094 − 1.812)/1.812 × 100 = −94.8%; speedup = 1.812/0.094 = 19.3×.

## Анти-паттерны

| Анти-паттерн | Почему плохо | Вместо этого |
|---|---|---|
| **Преждевременная оптимизация** | Усложняешь код ради 0.1% времени, которого нет на горячем пути | Сначала профиль; оптимизируй только красные фреймы из данных |
| **Оптимизация без замера** | «Я думаю, тут медленно» — интуиция про hotspot ошибается чаще, чем угадывает | Нет числа ДО → не трогай. Профиль определяет цель, не догадка |
| **Оптимизация не того** | Ускорил функцию, которая ест 2% времени → итоговый выигрыш ≤ ~2% (закон Амдала) | Бей в самый жирный фрейм; Amdahl: overall speedup ≤ 1/(1−p), p = доля времени, которую заняла оптимизированная часть |
| **Микробенчмарк-театр** | Меряешь `a+b` в изоляции с warm cache → числа не переносятся на прод | Мерь на реальном сценарии, прод-данных, с warm-up и перцентилями (p95/p99, не avg) |
| **Одна метрика = avg** | Среднее прячет хвост; p99 может быть 10× от mean | Всегда перцентили; SLA живёт в p95/p99, а не в среднем |
| **Фикс + рефакторинг разом** | Нельзя атрибутировать дельту: что помогло — фикс или рефактор? | Один фактор за раз, перемеряй после каждого |
| **Не перепрофилировал после фикса** | Bottleneck сместился, а ты оптимизируешь старый | После каждого фикса — новый профиль (шаг 7) |
| **Замер в debug-режиме** | DEBUG-логи / sourcemaps / dev-сервер искажают в разы | Меряй в prod-like: оптимизации компилятора, прод-конфиг, реальные данные |

## Границы / Red-flags — когда остановиться или эскалировать

**СТОП, дальше не оптимизирую, когда:**
- Метрика уже в **зелёной зоне** бюджета — дальнейший выигрыш не нужен (over-engineering).
- Очередной фикс даёт **< 10%** — закон убывающей отдачи, цена сложности выше выгоды.
- Выигрыш **в пределах шума** замера (Δ < 2σ от hyperfine/wrk) — это не улучшение, это дрожание.
- Упёрлись в **физический предел** (скорость сети/диска, теоретическая сложность алгоритма уже оптимальна).

**Эскалирую / меняю уровень, когда узкое место НЕ в коде:**
- Bottleneck в **инфраструктуре** (мало RAM/CPU, медленный диск, сетевой latency между ДЦ) → это scaling/деплой, не код. Скажи владельцу, не патчь код.
- Нужна **архитектурная смена** (шардинг БД, очередь, CDN, денормализация, кэш-слой) — это не «минимальный фикс». Подними как отдельное решение, не делай молча.
- Проблема **в стороннем сервисе/API** (внешний вызов медленный) → таймауты/ретраи/кэш на нашей стороне, но корень не у нас.

**Честно говорю «не знаю / нужно измерить», когда:**
- Не могу **воспроизвести** медленность → нет baseline, гадать запрещено (см. systematic-debugging). Прошу шаги/данные/нагрузку.
- Нет доступа к **прод-нагрузке/данным** → лабораторные числа могут не переноситься; помечаю как «оценка, не замер».
- Симптом **плавающий** (иногда быстро, иногда нет) → вероятно contention/GC/cold cache; нужен профиль именно в момент тормоза (`py-spy dump`, continuous profiling), а не усреднённый.

**Никогда:** не коммить временную профайлинг-инструментацию (`@profile`, debug-таймеры, `tracemalloc.start()` на горячем пути) в прод — это сама по себе деградация. Сними после диагностики.
