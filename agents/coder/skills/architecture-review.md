# Skill: Architecture Review + ADR

**Принцип:** архитектура — это набор решений, которые дорого менять. Оценивай не код, а **обратимость**, **blast radius** и **связанность**; всё, что переживёт спринт, должно быть записано в ADR с явными отвергнутыми альтернативами. *Решение без записанных альтернатив — это не решение, это привычка.*

## Когда активировать

- **Новый компонент / сервис / модуль** — до первой строки кода.
- **Крупный рефактор** (трогает >3 модулей, меняет публичный контракт, ломает миграцию).
- **Выбор технологии или хранилища** — БД, очередь, кэш, язык, фреймворк, внешний API.
- **Перед большим изменением**, которое трудно откатить (схема БД, формат данных, разбиение монолита, контракт между сервисами).
- Когда звучит «давай просто перепишем на микросервисы / добавим Kafka / вынесем в отдельный сервис» — **сначала ревью, потом код.**

Не активируй для: косметических правок, локальных багфиксов внутри одной функции, изменений без влияния на контракты/данные/границы. Two-way door внутри одного файла — просто делай.

## Измерения оценки (7 осей)

Оцени дизайн по каждой оси: 🟢 ок / 🟡 риск / 🔴 стоп. Любой 🔴 блокирует, пока не записан в ADR как осознанный trade-off.

| # | Ось | Что измеряем | Метрика / порог | 🔴 Red flag |
|---|-----|--------------|-----------------|-------------|
| 1 | **Связанность / Cohesion** | сцепление между модулями vs внутри | afferent/efferent coupling (Ca/Ce); Instability `I = Ce/(Ca+Ce)` ∈ [0,1]; LCOM ↓ = cohesion ↑ | модуль зависит от >5–7 других; цикл в графе зависимостей; «God object» >500 LOC / >20 методов |
| 2 | **Поток данных** | откуда данные, кто владелец, где мутируют | один writer на источник истины; направление зависимостей не образует цикл | два сервиса пишут в одну таблицу; данные текут «вверх» (low-level знает про high-level) |
| 3 | **Режимы отказа / Blast radius** | что упадёт, если упадёт это | blast radius = N зависимых компонентов; деградация vs полный отказ | синхронный fan-out (1 запрос → K downstream, все обязательны); отказ кэша = отказ системы; нет таймаута/ретрая/circuit breaker |
| 4 | **Масштабируемость** | где узкое место при ×10 нагрузки | stateless? горизонтально? Little's Law `L = λ·W`; пул соединений ≥ p99 concurrency | shared mutable state; единственный writer-узел без шардинга; O(N²) на горячем пути; неограниченный рост таблицы без TTL/партиций |
| 5 | **Границы консистентности** | где нужна транзакция, где допустим eventual | агрегат = граница транзакции; всё за её пределами — eventual + idempotency key | распределённая транзакция через 2 сервиса; «прочитал-изменил-записал» без оптимистичной блокировки; нет идемпотентности у ретраев |
| 6 | **Наблюдаемость** | сможем ли понять, что сломалось, в 3 ночи | три столпа: logs + metrics (RED: Rate/Errors/Duration) + traces; correlation_id сквозной | нет structured logging; ошибки глотаются; нет метрики на новый путь; долг «добавим логи потом» |
| 7 | **Обратимость (one-way / two-way door)** | можно ли откатить дёшево | two-way = откат < 1 дня без миграции данных; one-way = миграция/потеря данных/внешний контракт | необратимая миграция схемы без отката; публичный API без версионирования; формат хранения без миграционного пути |

**Door-эвристика (Bezos):** two-way door → решай быстро сам, не пиши ADR. **one-way door → обязателен ADR + явные альтернативы.** Если не уверен, к какому типу относится — считай one-way.

### Опорные эвристики и формулы

| Правило | Формула / порог | Источник |
|---------|-----------------|----------|
| **Instability** | `I = Ce / (Ca + Ce)`; стабильные модули I→0, изменчивые I→1 | Robert Martin |
| **Main Sequence (distance)** | `D = |A + I − 1|`; цель D→0 (не в «zone of pain» I=A=0, ни в «zone of uselessness» I=A=1) | Robert Martin, `A` = abstractness |
| **Little's Law** | `L = λ · W` (в среднем в системе = частота прибытия × время в системе) → размер пула/очереди | queueing theory |
| **Универсальная масштабируемость (USL)** | `C(N) = N / (1 + α(N−1) + βN(N−1))`; α=контеншн, β=когерентность → есть точка, после которой добавление узлов **снижает** throughput | Gunther |
| **CAP** | при partition выбираешь **C или A**, не оба; «CA» в распределённой системе не существует | Brewer |
| **Latency складывается, доступность перемножается** | синхронная цепь из K сервисов с доступностью a → `a^K`; 5×0.999 = 99.5% | — |
| **Стоимость изменения растёт во времени** | one-way door дешевле всего на этапе дизайна; цена ошибки ~×10 на каждой фазе после | — |
| **Закон Конвея** | система копирует структуру коммуникации команд → границы сервисов = границы команд | Conway |
| **Правило трёх** | абстрагируй после **3-го** дублирования, не раньше (защита от преждевременной абстракции) | — |

## Шаблон ADR (Architecture Decision Record)

Один ADR = одно решение = один файл `docs/adr/NNNN-kebab-title.md` (нумерация сквозная, монотонная). Формат Nygard.

```markdown
# ADR-NNNN: <короткое решение в одной фразе>

- **Статус:** Proposed | Accepted | Deprecated | Superseded by ADR-MMMM
- **Дата:** YYYY-MM-DD
- **Тип двери:** one-way | two-way
- **Участники:** <кто принимал решение>

## Контекст
<Какая проблема/сила вынуждает принять решение. Факты и ограничения, без выбора.
Что известно, какие нефункциональные требования (нагрузка, SLA, бюджет, сроки).>

## Рассматриваемые варианты
1. **<Вариант A>** — суть в одной строке.
2. **<Вариант B>** — ...
3. **<Вариант C / status quo>** — всегда включай «ничего не делать».

<Trade-off таблица — см. ниже. Минимум 2 реальные альтернативы, иначе это не выбор.>

## Решение
<Выбран вариант X. ПОЧЕМУ именно он — какие силы из Контекста перевесили.
Явно: что мы СОЗНАТЕЛЬНО приносим в жертву.>

## Последствия
**Плюсы (+):**
- ...

**Минусы / цена (−):**
- ...

**Принятый долг / что отложили:**
- <долг с условием выхода: «пересмотреть при >1000 RPS»>

**Триггер пересмотра:** <конкретное условие, при котором этот ADR надо переоткрыть>
```

**Правила ADR:**
- **Immutable.** Принятый ADR не редактируют — его *супершедят* новым (статус старого → `Superseded by ADR-MMMM`). История решений важнее «чистоты».
- Минимум **2 реальные альтернативы** + status quo. Один вариант = не выбор.
- Раздел «Минусы» обязателен и непуст. Решение без записанной цены — пропаганда, не ADR.
- Объём — 1 экран. ADR на 5 страниц никто не прочитает.

## Trade-off таблица (пример: выбор хранилища)

Вес критериев из Контекста (сумма = 1.0), оценка 1–5, итог = Σ(оценка×вес).

| Критерий | Вес | PostgreSQL | DynamoDB | Redis |
|----------|-----|-----------|----------|-------|
| Транзакции/консистентность | 0.30 | 5 | 2 | 2 |
| Горизонтальный скейл | 0.20 | 3 | 5 | 4 |
| Стоимость эксплуатации | 0.15 | 4 | 3 | 4 |
| Знакомость команде | 0.20 | 5 | 2 | 4 |
| Гибкость запросов | 0.15 | 5 | 2 | 1 |
| **Σ (взвешенно)** | 1.00 | **4.45** | **2.75** | **2.95** |

→ Вывод: PostgreSQL по сумме, потому что **транзакции и знакомость** доминируют в этом контексте; DynamoDB выигрывает только если вес «горизонтальный скейл» вырастет >0.5. **Это и есть триггер пересмотра ADR.**

> Веса — не объективная истина, а зафиксированный приоритет. Их явность и есть ценность: спор смещается с «какая БД лучше» (бесконечный) на «правильные ли веса» (решаемый).

## Как применять (алгоритм)

1. **Сформулируй решение в одной фразе.** Не можешь — значит, решений несколько; разбей на отдельные ADR.
2. **Классифицируй дверь.** one-way или two-way? Не уверен → one-way. Two-way внутри модуля → просто делай, ADR не нужен.
3. **Собери Контекст:** нефункциональные требования числами (RPS, p99, объём данных, рост/год, SLA, бюджет, дедлайн, размер/опыт команды). Без чисел оценка осей — гадание.
4. **Сгенерируй ≥2 альтернативы + status quo.** Status quo обязателен — иногда «не делать» выигрывает.
5. **Прогони каждый вариант по 7 осям.** Проставь 🟢/🟡/🔴. Любой 🔴 — либо устраняется дизайном, либо записывается как осознанный долг с триггером выхода.
6. **Построй trade-off таблицу:** критерии из Контекста → веса (Σ=1.0) → оценки 1–5 → взвешенная сумма. Веса фиксируй ДО оценок (иначе подгонишь под любимый вариант).
7. **Проверь анти-паттерны** (таблица ниже). Особенно: distributed monolith, преждевременная абстракция, resume-driven.
8. **Посчитай, где надо:** доступность цепи `a^K`, узкое место по Little's Law, точку насыщения по USL, blast radius (N зависимых).
9. **Запиши ADR** по шаблону. Минусы и триггер пересмотра — обязательны.
10. **Нарисуй минимальную схему** (C4-уровень Context/Container хватает): компоненты, направление зависимостей, синхронные vs асинхронные стрелки, границы транзакций. ASCII/Mermaid — достаточно.
11. **Назови самое дешёвое обратимое первое изменение.** Двигайся итеративно, не big-bang. Если можно начать с two-way door — начни с неё.

## Worked example

**Запрос:** «Вынесем загрузку файлов в отдельный микросервис, монолит уже большой.»

**Контекст (числами):** 40 RPS пиково, p99 = 300 мс, аплоады ~5% трафика, команда 3 человека, один деплой-пайплайн, общая Postgres-база. Рост ~2×/год.

**Door:** one-way ⚠️ — разрезание границы сервиса тянет за собой сеть, отдельный деплой, распределённые транзакции; откат = обратное слияние + миграция. → нужен ADR.

**Варианты:**
- A) Отдельный микросервис (как просили).
- B) Модуль-граница внутри монолита (модульный монолит): чёткий интерфейс `uploads/`, отдельная схема БД, но один процесс.
- C) Status quo (оставить как есть).

**Trade-off (вес из контекста: команда мала, нагрузка низкая → «операционная простота» весит много):**

| Критерий | Вес | A: микросервис | B: модуль | C: as-is |
|----------|-----|----------------|-----------|----------|
| Операционная простота (3 чел.) | 0.35 | 1 | 4 | 5 |
| Независимый деплой/скейл | 0.20 | 5 | 2 | 1 |
| Изоляция отказов (blast radius) | 0.20 | 4 | 3 | 2 |
| Цена миграции сейчас | 0.15 | 1 | 4 | 5 |
| Чистота границ | 0.10 | 4 | 4 | 1 |
| **Σ** | 1.00 | **2.70** | **3.40** | **3.20** |

**Оценка осей для A (микросервис):** Blast radius 🔴 (синхронный вызов монолит→upload, доступность падает до `0.999² = 99.8%`, +сетевой хоп к p99). Консистентность 🔴 (метаданные файла теперь в двух местах → распределённая транзакция или eventual + идемпотентность). Наблюдаемость 🟡 (нужен сквозной trace). Скейл 🟢 (но при 40 RPS не нужен).

**Решение:** вариант **B (модуль-граница)** — Σ=3.40, выше as-is (3.20) и микросервиса (2.70). Микросервис (A) проигрывает: при 3 разработчиках и 40 RPS платим всю операционную цену распределённой системы (CAP, сеть, два деплоя, distributed transaction) ради скейла, который **не нужен**. B даёт 90% пользы (чистая граница, отдельная схема) за 10% цены и оставляет дверь к A открытой.

**ADR-0007 (выдержка):**
```
# ADR-0007: Загрузка файлов — модуль-граница внутри монолита, не микросервис
- Статус: Accepted   Дата: 2026-06-16   Тип двери: one-way
## Решение
uploads/ как модуль с явным интерфейсом и отдельной схемой БД; один процесс, один деплой.
Сознательно жертвуем независимым скейлом загрузок.
## Последствия
+ Нет распределённых транзакций, нет лишнего сетевого хопа, один пайплайн.
+ Чёткая граница → вынос в сервис позже = механика, не редизайн.
− Скейл загрузок привязан к монолиту.
Принятый долг: при >500 RPS на загрузках ИЛИ отдельной команде на этот домен — переоткрыть, выносить в сервис.
Триггер пересмотра: загрузки >500 RPS устойчиво, либо специализированная команда.
```
**Первый обратимый шаг:** ввести интерфейс `UploadService` внутри монолита и отдельную схему — two-way door, откатывается за час.

## Анти-паттерны

| Анти-паттерн | Как выглядит | Чем плох | Лекарство |
|--------------|--------------|----------|-----------|
| **Resume-driven development** | «возьмём Kafka/k8s/Rust, потому что модно/для резюме» | сложность ради CV, а не задачи | критерий выбора — из Контекста задачи, не из трендов; запиши в ADR честную причину |
| **Преждевременная абстракция** | фабрика фабрик, плагин-система на 1 реализацию, интерфейс «на будущее» | сложность под нагрузку, которой нет; YAGNI | правило трёх: абстрагируй после 3-го дубля; начни с конкретного |
| **Distributed monolith** | «микросервисы», но деплоятся вместе, синхронно зовут друг друга, общая БД | худшее из двух миров: цена распределённости + связанность монолита | либо настоящая автономия (своя БД, async, независимый деплой), либо модульный монолит |
| **Over-engineering** | обобщение под гипотетические требования; 5 слоёв абстракции на CRUD | YAGNI; код дороже читать/менять | решай сегодняшнюю задачу; door-эвристика: two-way можно переделать дёшево потом |
| **Выбор без записанных альтернатив** | «решили использовать X» без сравнения | через полгода никто не помнит, почему; нельзя переоценить при смене контекста | ADR с ≥2 альтернативами + триггером пересмотра |
| **Big-bang rewrite** | «перепишем всё с нуля» | теряешь скрытые знания старой системы, долгая слепая зона | strangler fig: душить старое по кускам, всегда рабочая система |
| **Shared mutable state** | глобальный кэш/синглтон, в который пишут многие | гонки, невозможно масштабировать горизонтально | один writer / источник истины; иммутабельность; передавай данные, не разделяй |
| **Молчаливое заглатывание отказов** | `try/except: pass`, нет таймаута/ретрая | отказ невидим до 3 ночи; нет наблюдаемости | fail loud, structured log, метрика на каждый внешний вызов, явный таймаут |

## Границы / Red-flags — когда остановиться и сказать «не знаю»

- **Нет чисел в Контексте** (RPS, объём, SLA, бюджет) — оценка осей превращается в гадание. Скажи: «нужны нефункциональные требования числами, иначе это вкусовщина» и спроси их, не выдумывай.
- **3+ круга «починим архитектурой»** и каждый фикс вскрывает новую связанность — это не неудачная гипотеза, это неверная архитектура (см. systematic-debugging). Останови инкрементальные правки, выноси на отдельное решение.
- **One-way door с необратимой потерей данных** (миграция без отката, удаление, смена формата хранения) — НЕ решай молча. Эскалируй владельцу: цена ошибки несимметрична.
- **Решение упирается в орг-структуру** (закон Конвея: границы не совпадают с командами) — это не техническая проблема; назови её честно, не лечи кодом.
- **Требуют «просто скажи, что лучше»** без контекста — лучшая БД/язык/паттерн не существует в вакууме. Дай ответ только после Контекста или явно отметь допущения, на которых он держится.
- **Выходит за зону компетенции** (специфика домена: финансовый комплаенс, крипто, медицина, juridical) — отметь границу знания, не имитируй экспертизу. «Архитектурно — так; но domain-специфику X должен подтвердить эксперт».
- **Не уверен в обратимости** — считай решение one-way и пиши ADR. Цена лишнего ADR — 10 минут; цена пропущенного one-way — переписывание.
