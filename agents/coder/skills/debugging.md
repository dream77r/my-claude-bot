# Skill: Debugging — root-cause дисциплина

**Принцип:** сначала найди причину, потом чини. Фикс по симптому — это провал, даже если тест позеленел.

## The Iron Law

```
NO FIXES WITHOUT ROOT-CAUSE INVESTIGATION FIRST.
```

Не завершён Phase 1 — не имеешь права предлагать фикс. Нарушить букву этого процесса = нарушить его дух.

## Когда активировать

- Упавший тест, exception, traceback, 500, segfault, ханг, утечка памяти.
- «Работало вчера» / регрессия / flaky-тест / невоспроизводимый баг.
- **ОСОБЕННО** когда: time pressure, «очевидный quick fix», уже пробовал 2+ фикса, не понимаешь полностью.
- **НЕ пропускать**, если баг «простой»: у простых багов тоже есть root cause, а процесс на них быстр.

## Четыре фазы (последовательно, не перескакивать)

### Phase 1 — Root-cause investigation (ДО любого фикса)

| Шаг | Действие | Инструмент |
|-----|----------|------------|
| 1. Читай ошибку ЦЕЛИКОМ | стек-трейс до конца, file:line, error code, не пропускай warnings | `Read` |
| 2. Воспроизведи стабильно | точные шаги; каждый раз? Нет repro → собирай данные, не угадывай | `Bash` |
| 3. Проверь недавние изменения | `git log --oneline -20`, `git diff HEAD~5`, `git bisect` на регрессии | `Bash` |
| 4. Инструментируй границы | на каждой component boundary логируй in/out + config | `Edit`+`Bash` |
| 5. Трассируй data flow к истоку | откуда пришло bad value? Кто передал? Иди вверх до источника | `Grep` |

**Multi-component (API → service → DB, CI → build → deploy):** СНАЧАЛА добавь диагностику на каждую границу → прогони один раз → увидь, ГДЕ ломается → только потом копай этот компонент. Гипотеза о локации бага без evidence = угадывание.

### Phase 2 — Pattern analysis

1. **Найди рабочий пример** в том же коде — `Grep` по аналогичному вызову/паттерну, который работает.
2. **Сравни** с reference-реализацией ПОЛНОСТЬЮ (не skim) — каждую строку.
3. **Выпиши КАЖДОЕ отличие** working vs broken, каким бы мелким ни казалось. Не фильтруй «это не может влиять» — именно это и влияет.
4. **Зависимости:** какие config/env/версии/другие компоненты нужны и какие assumptions делает код.

### Phase 3 — Hypothesis & minimal test

1. **ОДНА гипотеза,** явно: «Корень — X, потому что Y». Конкретно, не размыто. Запиши.
2. **Минимальный тест:** самое маленькое изменение, одна переменная за раз. Не чини несколько вещей сразу.
3. **Верифицируй ДО продолжения:** сработало → Phase 4. Нет → НОВАЯ гипотеза, НЕ накладывай фикс на фикс.
4. **Не знаешь — скажи «не понимаю X».** Не имитируй понимание; исследуй или спроси.

### Phase 4 — Implementation

1. **Сначала падающий тест** — простейший repro, лучше автоматический (`pytest tests/...::test_x`). ОБЯЗАТЕЛЬНО до фикса — он должен краснеть.
2. **ОДИН фикс в истоке** — root cause, не симптом. Никаких «while I'm here» рефакторингов в этом же диффе.
3. **Верифицируй:** новый тест зелёный + весь suite зелёный (`python3 -m pytest tests/ -q`). Ничего не сломал.
4. **Фикс не сработал → STOP и считай попытки.** <3 → вернись в Phase 1 с новыми данными. **≥3 → под вопрос АРХИТЕКТУРА** (ниже), не делай фикс #4.

**Признаки архитектурной проблемы (после 3+ провалов):** каждый фикс вскрывает новый shared state/coupling в другом месте; фикс требует «большого рефактора»; каждый создаёт новый симптом рядом. Это НЕ провальная гипотеза — это неверная архитектура. Спроси: паттерн вообще здравый? Мы держимся за него по инерции?

## Как применять — алгоритм

```
1. READ ошибку/traceback целиком → выпиши file:line, error code, точный текст.
2. git log --oneline -20  +  git diff подозрительных файлов.   # «работало вчера» → git bisect.
3. Воспроизведи: запусти ровно упавший тест (pytest ...::test_x). Нет repro → собирай данные.
4. Grep по bad value / тексту ошибки вверх по call stack → найди исток, а не место падения.
5. Grep рабочий аналог → diff working vs broken → список отличий.
6. Сформулируй ОДНУ гипотезу → минимальный тест → проверь.
7. Падающий тест → один фикс в истоке → весь suite зелёный.
8. 3+ неудачных фикса → остановись, под вопрос архитектуру.
```

## Формат ответа

```
**Root cause:** <одно предложение — ПОЧЕМУ, не где падает>
**Доказательства:** <file:line, фрагмент лога/git diff, что именно доказывает причину>
**Fix:**
```diff
- broken
+ fixed
```
**Почему:** <почему это чинит ИСТОК, 1–2 предложения>
**Тест:** <падающий-до / зелёный-после, команда запуска>
```

## Пример (с реальным traceback)

Симптом: после `pip install -U pyjwt` тест `tests/test_auth.py::test_decode` падает с
`jwt.exceptions.DecodeError: It is required that you pass in a value for the "algorithms" argument when calling decode().`
«Работало вчера».

```
Phase 1: traceback → auth.py:88 decode_token() → jwt.decode(token, key) без algorithms.
         git log --oneline -10 → коммит a1b2c3 вчера «bump pyjwt 1.7→2.12».
         repro: pytest tests/test_auth.py::test_decode — падает 100%, тот же DecodeError.
Phase 2: рабочий аналог services/api.py:51 — там jwt.decode(token, key, algorithms=["HS256"]).
         Diff working vs broken: в auth.py отсутствует обязательный аргумент algorithms.
         Зависимость: PyJWT 2.0+ сделал algorithms обязательным (раньше дефолтил, теперь raise).
Phase 3: гипотеза — «Корень: decode() без algorithms; PyJWT 2.x raise вместо дефолта».
         Мин-тест: добавить algorithms=["HS256"] — одна переменная.
Phase 4: тест красный (DecodeError) → один фикс в истоке → зелёный, suite не тронут.
```

```
**Root cause:** PyJWT 2.0+ требует явный аргумент `algorithms` в jwt.decode(); код вызывал
                 jwt.decode(token, key) без него, и после bump 1.7→2.12 это стало DecodeError.
**Доказательства:** auth.py:88; git a1b2c3 «bump pyjwt 1.7→2.12»; рабочий api.py:51 передаёт
                    algorithms=["HS256"]; точный текст: DecodeError "...required ... algorithms ...".
**Fix:**
```diff
- payload = jwt.decode(token, key)
+ payload = jwt.decode(token, key, algorithms=["HS256"])
```
**Почему:** фикс в истоке — приводим вызов к контракту PyJWT 2.x, а не глушим DecodeError
            через try/except (это спрятало бы и реальные невалидные токены).
**Тест:** test_decode был red (DecodeError) → `pytest tests/test_auth.py -q` → зелёный.
```

> Примечание: `algorithms` обязателен в PyJWT начиная с 2.0.0 — это security-fix против
> algorithm-confusion атак, а не каприз. Не подавляй ошибку, передай реальный список алгоритмов.
> (Похожий класс: `ExpiredSignatureError` на просроченном токене — это ВАЛИДАЦИЯ exp, не
> отсутствие claim; не «чини» его, выдав новый токен в тесте без понимания, почему истёк.)

## Распространённые рационализации

| Отмазка | Реальность |
|--------|------------|
| «Баг простой, процесс не нужен» | У простых багов тоже есть root cause. На них процесс занимает минуты. |
| «Аврал, нет времени на процесс» | Системный подход БЫСТРЕЕ guess-and-check thrashing. |
| «Сначала попробую это, потом исследую» | Первый фикс задаёт паттерн. Делай правильно с начала. |
| «Тест напишу после, как фикс сработает» | Непокрытый фикс не держится. Тест-до доказывает, что баг был. |
| «Сразу несколько фиксов — быстрее» | Не изолируешь, что сработало. Плодит новые баги. |
| «Reference длинный, адаптирую паттерн» | Частичное понимание гарантирует баги. Прочитай целиком. |
| «Вижу проблему, сейчас починю» | Видеть симптом ≠ понимать root cause. |
| «Обёрну в try/except, и ошибки нет» | Глушение исключения прячет причину и реальные кейсы. Чини исток. |
| «Ещё одна попытка» (после 2+) | 3+ провала = архитектурная проблема. Под вопрос паттерн, не фикс снова. |

## Red-flags в мышлении — эти мысли значат STOP и возврат в Phase 1

- «Быстрый фикс сейчас, исследую потом» / «просто поменяю X и посмотрю».
- «Добавлю несколько изменений, прогоню тесты» / «пропущу тест, проверю руками».
- «Это наверное X, починю это» / «не понимаю полностью, но может сработать».
- «Reference говорит X, но я адаптирую иначе» / «вот главные проблемы: [список фиксов без investigation]».
- Предлагаешь решение ДО трассировки data flow / оборачиваешь ошибку в try/except вместо истока.
- **«Ещё одна попытка» (уже 2+)** / **каждый фикс вскрывает новую проблему в другом месте.**

## Границы — когда остановиться и эскалировать

- **Нет repro** после разумных попыток → не угадывай: добавь логи/observability, запроси у юзера точные шаги/версию/окружение.
- **Не понимаешь корень** — скажи «не знаю X» явно. Не выдавай гипотезу за факт.
- **3+ фикса не сработали** → стоп, эскалация к архитектурному решению, не фикс #4.
- **Heisenbug / race / железо / внешний API** — назови лимит наблюдаемости явно, не притворяйся, что поймал причину без доказательств.
- **Нетривиальный баг** — запиши root cause + fix в `memory/wiki/concepts/bugs.md` (через git_committer, не прямой git).
